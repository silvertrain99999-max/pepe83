# TREK Bike 상품관리·노출 최적화 운영 기준

기준일: 2026-10-10 · 적용: TREK 완성차 / 카페24 / 네이버 스마트스토어(스토어팜)

## 목적과 적용 범위

본사 → 매장 → 두 판매 채널의 옵션을 정확히 대조하고, 수정 후 저장된 값까지 확인한다. 훑어본 상품 수를 성과로 삼지 않는다. 사용자가 다시 손봐야 했던 항목은 미흡 사항으로 기록한다.

본 문서는 사용자와 합의한 완성차 업무 절차다. 기존 ACC `catalog.py`의 본사재고 기준이나 다른 공급사 정책을 변경하지 않는다. `bike_policy.py`는 **검토안 생성·범위 검사·완료 판정 코드**이며 웹사이트 자동 실행기가 아니다. 기존 `management/policy.py`도 계속 적용한다. 공통 정책이 허용하지 않는 예외를 코드 출력만으로 실행하지 않는다. 해당 상품에 대한 명시적 사용자 지시와 근거를 기록해 수동으로 처리한다.

판매중지 상품의 재개, 삭제, 신규 등록은 별도 지시 없이 실행하지 않는다. 사용자가 지시한 **재입고 옵션의 판매함 복원**은 상품 전체 판매중지 해제와 구분한다. SEO만 요청받은 경우 옵션·재고·가격·할인·배송·판매상태를 변경하지 않는다.

## 1. 작업 시작: 범위와 기준 시점 고정

1. 대상 모델·연식과 업무를 `inventory` 또는 `seo`로 구분한다.
2. 마지막 보고서는 위치를 찾는 참고자료로만 사용한다. 이번 작업 시점의 본사·매장·채널 상태를 다시 확인한다.
3. 본사 출처, 확인 시각(시간대 포함), 근거 버전, 작업자, 작업 사유를 남긴다. 이전 수치를 현재 재고로 재사용하지 않는다.
4. 사용자가 이미 확인한 내용은 사용자 제공 근거로 기록한다. 직접 검증한 결과로 바꾸어 표현하지 않는다.

정기 전수 순회를 기본값으로 두지 않는다. 입고·판매·가격 변경·신제품 등록·사용자 요청이 생겼을 때 해당 상품군을 처리하고, 트렉과 메리다의 검증된 절차를 축적한다. 메리다 사양이나 재고 규칙을 트렉에 그대로 적용하지 않는다.

## 2. 상품 및 옵션 대응

| 식별 항목 | 확인 방법 |
|---|---|
| 모델 / 연식 / 세대 | 국내 본사 상품과 채널 상세 사양 대조. 비슷한 상품명만으로 연결 금지 |
| 색상 / 사이즈 / SKU | 본사 옵션별 SKU로 연결. 번역 색상은 원문도 함께 보존 |
| 채널 식별자 | 카페24 상품번호·옵션번호, 스마트스토어 상품번호·옵션번호 각각 기록 |
| 전체 옵션 | 품절·판매안함 옵션도 포함해 누락·중복 검사 |

스마트스토어 검색은 등록기간 전체·판매상태 전체로 설정하고 상품번호 → SKU → 정확한 상품명 순으로 찾는다. SKU나 세대를 확인하지 못하면 추정 매칭하지 않는다. 세대가 적용되지 않는 경우 `n/a`를 명시한다. SKU 없는 매장 메모는 초안으로 보관하며 게시 준비 완료로 취급하지 않는다.

## 3. 재고 산정

본사 수량과 매장 실물 수량은 별도 열로 관리한다. 상품별 합의한 `supplier_only`, `store_only`, `supplier_plus_store` 중 하나를 사용한다. 기본값으로 합산하지 않는다.

- 본사 `보관 제품`·조회 실패·미등록은 **재고 미확인**이다. 0이나 단종으로 판정하지 않는다.
- 본사 미확인이라도 사용자가 매장 재고만 판매하도록 지시한 경우, 확인된 매장 수량과 `store_only` 근거로 진행한다.
- `50+` 같은 값은 정확한 50대가 아니라 하한이다. 원문과 해석을 남기고, 게시 수량으로 사용할 값은 별도 승인된 기준에 따른다.
- 매장 판매·예약·입고 변동을 반영한 가용 수량을 사용한다. 누락된 수량은 0이 아니다.
- 두 채널에 같은 실재고를 표시해도 물리 재고가 두 배가 되지 않는다. 주문 발생 시 양쪽 수량을 함께 갱신하는 운영 책임과 연동 여부를 확인한다.
- 연동 여부를 추정하지 않는다. 연동 중이면 덮어쓰기 경로·기준 채널을 확인하고, 독립 운영이면 양쪽을 각각 저장·검증한다.

## 4. 상품 하나를 끝내는 순서

1. 두 채널의 상품과 모든 옵션, 현재 판매상태·수량·가격·할인을 읽어 변경 전 상태를 보존한다.
2. 본사·매장 근거로 옵션별 변경안을 만들고 전체 옵션 대응을 검사한다.
3. 수량이 회복된 옵션은 사용자 지시에 따라 **옵션 판매함**까지 반영한다. 수량만 늘리고 판매안함을 남기면 미완료다.
4. 0인 옵션은 재고와 품절 표시를 확인한다. 일부 품절을 상품 전체 판매중지로 바꾸지 않는다.
5. 가격 변경이 범위에 있으면 정상가·판매가·옵션 추가금·기존 할인 조건을 별도 대조한다. 기존 할인을 자동 삭제하거나 재계산하지 않는다.
6. 카페24 저장 → 다시 열어 값 확인 → 스마트스토어 저장 → 다시 열어 값 확인 순으로 처리한다. 순서는 접속 상황에 따라 바꿀 수 있으나 두 채널 모두 마무리한다.
7. 구매 화면에서 해당 색상·사이즈가 선택 가능한지, 재입고 옵션을 실제 주문할 수 있는 상태인지 확인한다. 확인 불가 항목은 별도 미검증으로 남긴다.
8. 최종 수량과 판매 상태를 관리표에 반영하고 다음 상품으로 이동한다.

## 5. 완료 판정과 장애 복구

단계: `not_checked → matched → edited → saved → reverified`. 사용자 완료 통보만 받은 경우 `user_reported`로 따로 기록한다. 저장 완료 안내는 `saved`의 근거이며 재조회 근거를 대신하지 못한다.

완료 기록에는 채널·상품번호·옵션번호·업무·수정자·검증자·목표값·실제값·저장 근거·재조회 근거·시각을 남긴다. 상품관리 완료와 SEO 완료를 별도로 집계한다. `verified()`에는 해당 업무의 전체 목표값을 전달해야 하며 재입고 옵션은 수량과 `option_selling`을 모두 포함한다. 증거의 진위와 최신성을 코드가 자동 인증하지는 않는다.

로그인 만료·저장 알림·응답 지연 발생 시:

- 현재 상품번호, 입력한 값, 마지막 확인 단계, 다음 행동을 체크포인트로 남긴다.
- 저장 알림이 늦게 나타날 수 있으므로 화면·대화상자를 다시 관찰한다. 처음 알림이 없었다는 이유로 저장 버튼을 반복 클릭하지 않는다.
- 재연결 후 상품을 다시 열어 저장값부터 확인한다. 이미 반영된 값을 중복 처리하지 않는다.
- 같은 원인의 실패가 반복되면 멈추고 구체적인 복구 행동만 요청한다. 로그인은 사용자에게 맡긴다.
- 검증 오류가 재고·판매상태 변경을 요구하면 SEO 작업에서 임의 승인하지 않고 보류한다.

## 6. 상품 노출 최적화

### 최우선: 상품명 만드는 기준

상품명을 먼저 정돈한 뒤 검색어·태그·설명을 작성한다. [공통 상품명 작성 기준](../docs/YBBIKE_작업분류코드_v1.md)을 적용한다.

`두 자리 연식 + 트렉 + 모델 + 세대(해당 시) + 구동계 + 뒤 기어 단수 + 프레임 소재 + 차종`

연식·브랜드·정확한 모델명을 앞에 두고 구매 판단에 필요한 사양을 이어 적는다. 모든 항목을 억지로 채우지 않는다. 세대·Di2·AXS 등 실제 모델 차이를 만드는 표기를 유지한다. 색상·사이즈는 옵션에서 구분하되 별도 상품이면 제목에도 넣는다. 통학·입문·출퇴근 같은 용도 검색어는 검색설정과 설명에 배치한다.

카페24와 스마트스토어에 동일한 상품명을 사용한다. 정확한 국내 연식별 사양이 확인된 요소만 기재한다. 카본 포크를 카본 프레임으로 표현하지 않는다. 전자식/기계식 구동계를 구분하고, 총 기어 수를 뒤 기어 단수와 혼동하지 않는다. 중복 단어·과도한 기호·가격·재고·홍보 문구는 제목에 넣지 않는다.

### 검색 의도와 필드

| 범위 | 설정 |
|---|---|
| 모델 검색 | 브랜드, 모델, 연식, 세대 표기를 일치시킨다 |
| 사양 검색 | 검증된 구동계, 단수, 프레임 소재, 브레이크 유형을 필요한 곳에 사용 |
| 용도 검색 | 실제 제품에 맞는 출퇴근·통학·운동·장거리·여행 등으로 확장 |
| 청소년 수요 | 제품에 적합할 때 통학·입문 용도를 설명. 인기 순위나 모든 청소년에게 맞는 사이즈를 주장하지 않음 |
| 카페24 | 상품명, 자체 검색어, Title, Author=YBBIKE, Description, Keywords, 이미지 Alt |
| 스마트스토어 | 상품명, 정확한 카테고리·브랜드·속성, Page Title, Meta description, 등록 가능한 관련 태그 |

태그 후보는 현재 관리자 화면의 등록 가능 여부·길이·정책을 확인한다. 모든 검색어를 억지로 태그에 넣지 않는다. 메타 키워드 입력만으로 노출 개선이나 순위 상승을 보장하지 않는다. 검색 설명은 읽을 수 있는 문장으로, 이미지 Alt는 해당 이미지의 제품을 간결하게 설명한다.

SEO 저장 후 두 채널의 상품명·검색정보를 재조회한다. 변경 전후의 검색 노출·클릭·유입 검색어·전환 지표는 확인 가능한 범위에서 같은 기간 기준으로 비교한다. 재고·가격·계절·광고 변화도 함께 기록해 SEO의 효과로 단정하지 않는다. 낮은 노출은 분류·속성·판매 가능 여부부터, 낮은 클릭은 제목·대표이미지부터, 낮은 전환은 옵션·가격·배송·상세정보부터 점검한다.

## 7. 코드 사용 및 유지보수

```sh
python trek/bike_policy.py inventory PRIVATE_INVENTORY_INPUT.json
python trek/bike_policy.py seo PRIVATE_VERIFIED_SPEC.json
python -m unittest discover -s trek -p "test_*.py" -v
```

입력 형식의 실행 가능한 예시는 `test_bike_policy.py`의 `fixture()`와 SEO 테스트에 있다. 모든 예시는 가상 데이터다. 필수 근거는 `reference`, `checked_at`, `revision`, `confirmed=true`이며 실제 확인 후에만 작성한다. 재실행만으로 확인 시각이나 근거 버전을 갱신하지 않는다. 출력 `review_plan`은 적용 완료가 아니다. 오류 시 `hold`, 빈 변경안, 종료 코드 2를 반환한다.

코드화한 내용: 재고 산정·전체 옵션 대응·판매함 복원 지시·SEO 제목/필드 생성·업무 범위·두 채널 재조회 일치 판정. UI 조작, 실시간 수집, 가격 변환, 구매 화면 확인, 통계 수집은 실행자가 담당한다.

GitHub에는 운영 규칙·가상 예시·검사 코드·테스트만 저장한다. 실재고표, 매출, 계정, 토큰, 고객·주문정보, 비공개 본사 화면은 올리지 않는다. 새로 발견한 예외는 원인 → 처리 기준 → 검증 방법 → 회귀 테스트 순으로 축적한다. 공급사 화면 변경은 재검증하고 실패했던 절차를 반복하지 않는다.
